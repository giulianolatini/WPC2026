05 — Team di agenti per lo sviluppo spec-driven

Questo documento descrive un team di agenti orchestrato per sviluppare un progetto software con GitHub Copilot in VS Code. Il team usa i modelli configurati con chiavi proprie (BYOK): modelli costosi per analisi e pianificazione, modelli economici per l'implementazione. I file del team sono in examples/agents/. Il documento 06 spiega il BYOK; il documento 07 presenta il gateway LiteLLM.

Ogni figura è un file in examples/agents/.github/agents/. Il file contiene il modello, gli strumenti permessi e le istruzioni (S-007, S-072).

3. Architettura

  • Il PO parla con due agenti: Organizzatore e Pianificatore. Le altre figure sono subagent nascosti dal selettore degli agenti (user-invocable: false).
  • L'Organizzatore chiama Tester, Sviluppatore, Operativo, Scrittore e i due Reviewer. Il Pianificatore chiama solo l'Avversario.
  • Le figure comunicano con i file del repository: specifiche, backlog, test, codice, log. Chi chiama un subagent scrive un compito completo: il subagent lavora in un contesto separato (S-165).

Copilot come harness. VS Code e l'harness Copilot eseguono il ciclo dell'agente: leggono il file .agent.md, offrono gli strumenti (read, edit, execute…), applicano i permessi. Il modello scelto riceve il prompt tramite l'API del suo provider, con la chiave del PO (06 §1).

4. Modelli e costi

Criterio: il costo del modello segue la quantità di ragionamento del compito. Il Pianificatore ragiona su tutto il progetto; le figure operative lavorano su task atomici.

Figura Provider Modello Effort Prezzo input / output (USD per 1M token)
Pianificatore Anthropic claude-fable-5-2 high 8 / 40
Organizzatore Anthropic claude-sonnet-5-5 default 2 / 10
Avversario OpenAI gpt-6.1-sol low 2 / 10
Sviluppatore, Operativo OpenAI gpt-6-luna default 0,10 / 0,50
Tester OpenRouter z-ai/glm-5.3 default 0,0699 / 1,40
Scrittore Anthropic claude-haiku-5-5 default 0,10 / 0,50 fino a 100K token di prompt; poi 0,50 / 2,50
Reviewer ottimista OpenRouter deepseek/deepseek-v4.1-flash default 0,0507 / 0,2028
Reviewer antagonista OpenRouter qwen/qwen3.5-397b-a17b, provider novita → venice → gmicloud default 0,39 / 2,34 (varia per provider)

Fonti dei prezzi: S-040, S-102 e listino OpenRouter, verificati con P-12 il 2026-11-14. I prezzi cambiano: controlla il listino prima di usare il team.

  • I due Reviewer usano due modelli diversi: due punti di vista e due «famiglie» di errori.
  • L'Avversario usa un provider diverso dal Pianificatore, con effort low: il ragionamento limitato evita più di 2 alternative.
  • gpt-5.4-mini non è più la scelta: è della generazione precedente e costa più di gpt-6-luna. gpt-5.3-codex è deprecato (D-037).
  • qwen/qwen3-coder ha un punteggio basso nelle chiamate agli strumenti (46,2% su τ²-Bench): il Reviewer antagonista usa qwen/qwen3.5-397b-a17b (79,1%) con i provider che hanno meno errori di tool call (P-12).
  • Anthropic presenta claude-haiku-5-5 per classificazione, estrazione e instradamento, non per il coding: per questo resta solo allo Scrittore.
  • I file di esempio in examples/vscode/ e examples/litellm/ contengono il modello del Reviewer antagonista. Aggiungi gli altri modelli del team dal Language Models editor (06 §4).

6. Installazione del team in un repository

Requisiti: VS Code con GitHub Copilot (01), modelli BYOK di Anthropic, OpenAI e OpenRouter (02 §3), git, gh, .NET SDK 10, PowerShell 7.4 o successivo, GitHub Spec Kit 1.4.0 (02 Appendice A).

  • Crea i rami main e develop nel repository del progetto.
  • Crea un ramo feature/000-team-agenti da develop.
  • Inizializza Spec Kit nella cartella del progetto e installa l'estensione git (P-13):
specify init --here --force --integration copilot
specify extension add git
  • Copia il contenuto di examples/agents/ nella radice del repository. La copia sostituisce git-config.yml dell'estensione git: da quel momento Spec Kit crea rami feature/<NNN>-<slug>.
cp -R examples/agents/. /percorso/del/progetto/

Copy-Item -Recurse -Force examples\agents\* C:\percorso\del\progetto\
Copy-Item -Recurse -Force examples\agents\.github C:\percorso\del\progetto\
Copy-Item -Recurse -Force examples\agents\.specify C:\percorso\del\progetto\
Copy-Item -Force examples\agents\.gitignore C:\percorso\del\progetto\
  • Se il progetto ha già un .gitignore, aggiungi la riga .team/ invece di copiare il file.
  • Sostituisci @release-approver in .github/CODEOWNERS con l'utente GitHub del PO.
  • Attiva le due impostazioni dell'harness Copilot (§5).
  • Apri il progetto in VS Code. Per ogni file in .github/agents/ controlla il campo model: cancella l'ID e accetta l'ID che il completamento propone per il tuo modello BYOK ⚠️.
  • Applica la baseline di sicurezza (03 §7).
  • Apri la PR verso develop e uniscila. Porta ci.yml e CODEOWNERS anche su main.
  • Dopo la prima esecuzione verde di ci.yml, applica i ruleset (§9). ⚠️ ci.yml richiede una soluzione .NET nella radice del repository e un test Pester in tests/: il passo S-916 del runbook crea una soluzione minima.

Esito atteso: il selettore degli agenti mostra Organizzatore e Pianificatore. Le altre figure non compaiono nel selettore.

7. Uso del team

La procedura con comandi, parametri ed evidenze è la fase F9 del runbook.

7.1 Pianificazione

  • Seleziona l'agente Pianificatore e descrivi l'esigenza.
  • Rispondi alle domande. Per le scelte importanti il Pianificatore presenta il what-if dell'Avversario.
  • Di' al Pianificatore quando le scelte sono complete. Il Pianificatore pianifica una Feature alla volta: crea il ramo feature/<NNN>-<slug> da develop, scrive specs/, docs/backlog/ e aggiorna docs/team/writing-rules.md su quel ramo. La pianificazione arriva in develop con la PR della Feature.
  • Leggi il backlog. Controlla i criteri di accettazione dei Task e la Definition of Done di ogni epic.md e feature.md. Approva o chiedi modifiche.

7.2 Sviluppo di una Feature

  • Seleziona l'agente Organizzatore e chiedi di sviluppare la Feature (es. E01-F01).
  • Per ogni task l'Organizzatore chiama, in ordine: Tester (red), Sviluppatore o Operativo (green e refactor), Scrittore.
  • L'Organizzatore apre la PR verso develop, compila le evidenze della Definition of Done e chiama i due Reviewer.
  • Se i due Reviewer approvano e le voci da DoD-F1 a DoD-F7 sono soddisfatte, l'Organizzatore unisce la PR, registra DoD-F8 e DoD-F9 e ti presenta il riepilogo con le evidenze.

7.3 Release

  • Chiedi all'Organizzatore di preparare la Release. L'Organizzatore crea release/<versione> da develop.
  • Il Tester scrive ed esegue i test d'integrazione.
  • I due Reviewer esaminano la PR verso main e la Definition of Done dell'Epic.
  • Leggi il riepilogo, approva la PR in modo esplicito ed esegui tu il merge in main.
  • L'Organizzatore apre la PR di riallineamento verso develop.

8. Definition of Done

Regola. Lo sviluppo di una Feature o di un'Epic è concluso solo quando la sua Definition of Done è completa: ogni voce è soddisfatta e ha un'evidenza (D-038).

La Scrum Guide definisce la Definition of Done come la descrizione formale dello stato che il prodotto deve avere per rispettare le misure di qualità richieste; un lavoro che non la rispetta non si rilascia (S-170). Il template applica lo stesso principio a Feature ed Epic.

Criteri di accettazione Definition of Done
Domanda «Questo Task fa quello che deve fare?» «Questa Feature (o Epic) è finita?»
Livello Task Feature, Epic
Contenuto Diverso per ogni Task Uguale per tutte le Feature (o per tutte le Epic)
Forma «Dato…, quando…, allora…» con il campo Verifica Tabella: voce, soddisfatta, evidenza

I criteri di accettazione da soli non bastano: descrivono il comportamento, non lo stato di qualità. Il team li rende verificabili (un comportamento, un valore esatto, un test) e li usa come prima voce della Definition of Done.

Dove si applica la regola

Punto Figura Azione
epic.md, feature.md Pianificatore Scrive in testa l'obiettivo di completamento e la tabella con tutte le voci standard
Prima delle review Organizzatore Compila la colonna Evidenza con comandi ed esiti reali
Review Reviewer ottimista e antagonista Controllano le voci che esistono prima delle review (da DoD-F1 a DoD-F6; da DoD-E1 a DoD-E5): soddisfatta, non soddisfatta o senza evidenza; non approvano con una voce aperta
Merge Organizzatore (in develop), PO (in main) Unisce solo con le voci richieste per il merge: da DoD-F1 a DoD-F7 per develop, da DoD-E1 a DoD-E6 per main
Stato done Organizzatore Lo assegna solo con tutte le voci soddisfatte, comprese quelle che esistono dopo il merge (DoD-F8, DoD-F9; DoD-E7, DoD-E8)

Le voci standard (da DoD-F1 a DoD-F9 per una Feature, da DoD-E1 a DoD-E8 per un'Epic) sono in backlog.md. I modelli dei file sono in templates/. Solo il PO può togliere una voce.

9. GitFlow, protezione dei rami e regola di qualità

Il template usa GitFlow (S-167): feature/* → develop → release/* → main, più hotfix/*. Le regole complete sono in gitflow.md.

Questo repository (WPC2026) usa GitHub Flow. GitFlow vale per il repository che riceve il template.

9.1 Protezione dei rami

Le istruzioni di un agente non sono un controllo: GitHub deve rifiutare le operazioni non permesse (D-039).

Elemento File del template Funzione Fonte
Ruleset main-develop .github/rulesets/main-develop.json PR obbligatoria, controlli di stato, nessun force-push, nessuna eliminazione, nessun bypass S-171, S-172
Ruleset main-release-approval .github/rulesets/main-release-approval.json 1 approvazione di un code owner per main S-172
CODEOWNERS .github/CODEOWNERS Solo il PO: un ruleset non può nominare un utente S-173
CI .github/workflows/ci.yml Produce i controlli build, test-dotnet, test-powershell S-176
Script scripts/Set-Rulesets.ps1 Crea o aggiorna i ruleset con la REST API S-174
  • gh pr merge --admin usa i privilegi di amministratore per unire una PR che non rispetta i requisiti (S-175). Per questo l'agente non usa il token del PO.
  • Identità separata. L'Organizzatore usa una GitHub App o un account di servizio con i soli permessi Contents: write e Pull requests: write, senza Administration, senza Workflows e fuori dalla lista di bypass (S-177). Il PO è l'unico code owner.
  • Controlli di stato e workflow. ci.yml gira dal ramo della PR: chi può modificare il workflow può rendere verdi i controlli. Senza il permesso Workflows l'agente non può modificare .github/workflows/. Resta il rischio di test modificati in una PR verso develop, che non richiede approvazioni: il Reviewer antagonista lo controlla (D-043).
  • Il caso svolto examples/speckit-ruleset/ contiene la specifica, il piano e i test che verificano il rifiuto di --admin.
  • ⚠️ Niente di questo è stato provato su GitHub. Con il piano Free i ruleset funzionano solo nei repository pubblici; per i repository privati servono i piani Pro, Team o Enterprise Cloud (S-171). Il bypass di un team richiede un'organizzazione.

9.2 Regola di qualità di main

Obiettivo del PO: gli artefatti prodotti da main non contengono eccezioni non gestite e non si fermano per un'anomalia prevedibile.

Nessuna pratica garantisce che un processo non termini mai: l'evento AppDomain.UnhandledException notifica l'errore, non lo annulla (S-179, P-13). Il team applica quattro controlli:

  1. il Pianificatore scrive un criterio di accettazione per ogni input non valido e ogni errore previsto;
  2. il Tester scrive un test per ognuno di questi criteri (voce DoD-F4) e i test d'integrazione della Release (voce DoD-E3);
  3. chi implementa valida gli input e cattura solo le eccezioni da cui il codice può riprendersi (S-178); un gestore globale registra l'errore prima della terminazione (S-179);
  4. il Reviewer antagonista controlla le evidenze della voce DoD-E4 e assegna severità alta a ogni eccezione non gestita in una PR verso main; il suo esito entra nella voce DoD-E6.

10. Sicurezza

  • Privilegio minimo. Ogni figura ha solo gli strumenti necessari: i Reviewer e l'Avversario leggono soltanto; il Pianificatore usa il terminale solo per Spec Kit e per il ramo della pianificazione; solo l'Organizzatore usa gh per le PR (03 §3).
  • Segreti. Le istruzioni di ogni figura vietano di leggere .env, chiavi e token. Mantieni attiva la sandbox dell'agente (03 §7).
  • Codice verso i provider. Con il BYOK il codice del progetto va ai provider dei modelli. Tre figure usano OpenRouter (Tester e i due Reviewer): configura i guardrail dell'account (provider permessi, nessuna conservazione dei dati) prima di usare il team su codice riservato (S-115, S-151). allow_fallbacks vale solo nella singola richiesta (P-12).
  • Merge. L'Organizzatore unisce solo in develop. I ruleset e l'identità separata impediscono il merge in main senza l'approvazione del PO (§9.1).
  • Prompt injection. Un file del repository o una pagina web possono contenere istruzioni per l'agente. Nessuna figura ha lo strumento web: il Pianificatore ha execute per gli script di Spec Kit, e un agente con web ed execute insieme può eseguire istruzioni lette da una pagina (D-043, 04).
