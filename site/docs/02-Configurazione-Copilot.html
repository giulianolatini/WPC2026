02 — Configurazione di GitHub Copilot in Visual Studio Code con LLM via API

Questo documento descrive come GitHub Copilot in VS Code usa modelli di provider esterni. Confronta due percorsi: configurazione nativa (BYOK diretto verso ogni provider) e gateway LiteLLM (un solo endpoint locale verso tutti i provider).

Prerequisiti: 01-Installazione.md. Decisioni di riferimento: D-003, D-007, D-008, D-013, D-015…D-021.

La review con Perplexity (P-01…P-08) ha corretto questa versione: vedi il registro in Review-Perplexity.md.

1. Uso di GitHub Copilot in VS Code

GitHub Copilot in VS Code offre queste funzioni:

Funzione Descrizione Modelli BYOK
Inline suggestions, Next Edit Suggestions (NES) Suggerimenti di codice durante la scrittura No: richiedono account GitHub e piano Copilot (S-001, S-070)
Chat view Conversazione con il modello nella barra laterale Sì
Inline chat Chat nell'editor, sul codice selezionato (inlineChat.defaultModel) Sì
Agents Un agente esegue un'attività con strumenti (file, terminale, MCP). Chat view e Agents window eseguono agenti (S-008) Sì, solo modelli con tool calling
Utility tasks Titoli, sommari, messaggi di commit, descrizioni di PR Sì, con chat.utilityModel / chat.utilitySmallModel
Semantic search, embeddings Indicizzazione e ricerca nel workspace No (S-001)

Harness. Un harness è il motore che esegue l'agente. Il cambio di modello non cambia l'harness (S-068).

Harness Dove esegue Accesso ai modelli BYOK
Copilot Copilot SDK nell'Agent Host; la sessione continua anche dopo la chiusura della finestra; Chat view e Agents window GitHub Copilot Sperimentale: chat.agentHost.byokModels.enabled
Local Harness integrato, nell'extension host; la sessione si ferma con la finestra; solo Chat view Provider configurati Sì, anche senza account GitHub e senza piano Copilot
Claude Claude Agent SDK, nel workspace o in un worktree Credenziali Anthropic o modelli instradati da Copilot Credenziali proprie dell'harness
Codex Estensione OpenAI Codex o integrazione sperimentale con l'Agent Host Abbonamento Copilot (Pro+) o account ChatGPT No

Fonti: S-001, S-068. Cloud non è un harness: è una destinazione di esecuzione (sperimentale) dell'harness Copilot (S-068).

La demo usa l'harness Local per i modelli BYOK: è il percorso completo e non sperimentale. Un modello BYOK non configura gli harness Claude e Codex (S-001, D-003).

Messaggio chiave del talk. Il BYOK cambia il modello. Non cambia l'esperienza: chat, agenti, strumenti, istruzioni e skill restano gli stessi.

2.2 Tipi di modello (model picker)

Il Language Models editor gestisce i modelli. Aprilo con l'icona a ingranaggio nel model picker, o con il comando Chat: Manage Language Models (S-001).

2.5 Policy per Copilot Business ed Enterprise

Meccanismo Dove si configura Effetto Fonte
BYOK configurato dall'utente (local BYOK) Policy Bring Your Own Language Model Key in VS Code. Attiva di default: l'amministratore la può disattivare Le chiavi restano sul client; le richieste vanno direttamente al provider S-018, S-015
BYOK configurato da enterprise/organizzazione (public preview) Enterprise: AI controls → Copilot → Configure custom models → Add API key. Delega alle organizzazioni con la policy Enable custom models; organizzazione: Settings → Copilot → Models → Custom models Chiavi lato server; i modelli passano dalla Copilot API a tutti gli utenti con licenza S-015, S-019, S-101

⚠️ Fonti non coerenti. Il changelog GitHub dice che la policy è "enabled by default" (S-018). La FAQ di VS Code dice ancora che l'amministratore "must enable" la policy (S-071). Se il model picker non mostra Manage Language Models, chiedi all'amministratore di controllare la policy (D-013).

Fatturazione. Il BYOK locale non consuma crediti Copilot: il provider fattura le chiamate (S-018). Dal 2026-06-01 Copilot usa i GitHub AI Credits al posto delle premium requests (S-100).

Piani individuali (Free, Pro, Pro+, Max, Student). Nessuna policy: il BYOK locale è disponibile nel Language Models editor. Il BYOK funziona anche senza piano Copilot, nell'harness Local (S-001, P-02).

Altri client con BYOK locale: JetBrains, Xcode, Copilot CLI, GitHub Copilot app, Copilot SDK (S-015). La policy IDE non controlla il BYOK di Copilot CLI (P-02).

3. Configurazione nativa verso i provider

3.0 Procedura comune

  • Apri il Language Models editor: Chat: Manage Language Models.
  • Seleziona Add Models.
  • Seleziona il provider (built-in, da estensione, o Custom Endpoint).
  • Inserisci un nome di gruppo.
  • Inserisci la chiave API o i dettagli dell'endpoint.
  • Se VS Code apre chatLanguageModels.json, completa i dettagli del modello.
  • Seleziona il modello nel model picker della Chat view.
  • Se il modello non è visibile, riavvia VS Code.

Fonte: S-001.

Chiavi nei comandi. Negli esempi curl la chiave passa da stdin (printf … | curl -H @-): non compare negli argomenti del processo (01 §7). Chiavi API. Nei file JSON usa sempre una variabile di input ("${input:nome}"), non la chiave in chiaro (S-001). Header di autenticazione. Con apiType: messages VS Code invia x-api-key; con URL Azure OpenAI invia api-key; negli altri casi Authorization: Bearer <apiKey>. Con requestHeaders puoi aggiungere header; il token ${apiKey} diventa la chiave configurata (S-071). Agenti. Solo i modelli con tool calling sono visibili per gli agenti (S-001). Token. La somma di maxInputTokens e maxOutputTokens non deve superare la finestra di contesto del modello (S-001).

3.1 Claude.AI (Anthropic API)

Voce Valore
Provider Anthropic (built-in)
Chiave ANTHROPIC_API_KEY dalla Claude Console
Modelli esempio claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5 (S-040)
Endpoint https://api.anthropic.com/v1/messages (S-040)
  • Esegui la procedura comune con il provider Anthropic.
  • Verifica la chiave fuori da VS Code (S-040):
printf 'x-api-key: %s\n' "$ANTHROPIC_API_KEY" \
  | curl https://api.anthropic.com/v1/messages -H @- \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{"model": "claude-sonnet-5-5", "max_tokens": 64, "messages": [{"role": "user", "content": "Hello"}]}'

2026-10-21 è la versione API raccomandata. Rimuove temperature, top_p e top_k: se li invii, l'API restituisce 400 (S-116, D-021).

Il livello di thinking si imposta dal model picker. L'impostazione github.copilot.chat.anthropic.thinking.effort è deprecata (S-001).

3.5 Hugging Face (estensione ufficiale o Custom Endpoint)

Percorso principale — estensione (S-048, D-008):

  • Crea un token fine-grained con il permesso Make calls to Inference Providers (S-047).
  • Installa l'estensione Hugging Face Provider for GitHub Copilot Chat (VS Code ≥ 1.104.0) (S-048, S-049).
  • Apri il model picker → Manage Models… → Hugging Face.
  • Inserisci il token.
  • Seleziona i modelli da aggiungere al model picker.

Se il provider Hugging Face non è visibile, aggiorna VS Code e ricarica la finestra (S-048).

Percorso alternativo — Custom Endpoint verso il router OpenAI-compatible https://router.huggingface.co/v1 (S-047):

{
  "name": "Hugging Face Router",
  "vendor": "customendpoint",
  "apiKey": "${input:hfToken}",
  "apiType": "chat-completions",
  "models": [
    {
      "id": "openai/gpt-oss-120b:groq",
      "name": "HF · gpt-oss-120b (groq)",
      "url": "https://router.huggingface.co/v1/chat/completions",
      "toolCalling": true,
      "vision": false,
      "maxInputTokens": 112000,
      "maxOutputTokens": 16000
    }
  ]
}

Il suffisso dell'ID sceglie il provider di inferenza: :fastest (default), :cheapest, :preferred, oppure :<provider> (es. :groq) (S-047). L'esempio fissa :groq: così sai quale provider tratta i dati (04 AZ-06).

4. GitHub Copilot con LiteLLM come gateway

4.1 Quando usare un gateway

LiteLLM proxy espone un solo endpoint locale. Traduce le richieste nei formati dei provider (S-022). La scelta tra nativo e gateway dipende dal contesto (D-017).

Criteri di scelta

Contesto Raccomandazione
Singolo sviluppatore, pochi provider Nativo. Nessun componente in più, nessun punto singolo di guasto
Team con chiavi condivise, budget, allowlist di modelli, log centralizzati Gateway, con hardening (sotto)
Organizzazione su Copilot Business/Enterprise Valuta prima l'Enterprise BYOK di GitHub (§4.6)
Uso di thinking Anthropic con tool Nativo, o gateway con apiType: messages (D-019)

Confronto

Aspetto Nativo LiteLLM
Chiavi dei provider Su ogni client VS Code (secret storage) Solo sul gateway (.env o DB)
Chiave sul client 5 1 (virtual key)
Impatto di una compromissione Una chiave di uno sviluppatore Tutte le chiavi di tutti i provider (S-104)
Nomi dei modelli ID del vendor Alias stabili (model_name)
Formato API verso VS Code Nativo del provider chat-completions, responses, messages tradotti (S-028, S-029)
Thinking Anthropic con tool Preservato A rischio con chat-completions (S-110)
Cambio di modello Riconfigura ogni client Modifica config.yaml e riavvia
Budget, spend log, chiavi per utente No Sì, profilo esteso con PostgreSQL (S-020)
Latenza aggiunta — Pochi ms dichiarati dal vendor; trascurabile (P-08)
Componenti da gestire Nessuno Servizio, aggiornamenti di sicurezza, DB (profilo esteso)
Punto singolo di guasto No Sì, compensato in parte da fallback e routing

Rischi del gateway (2026)

  • Supply chain: release compromesse 1.82.7, 1.82.8 (marzo) e 1.107.0 (ottobre), con tag mobili Docker compromessi (S-104, S-105).
  • Vulnerabilità: CVE critiche nel proxy, tra cui CVE-2026-114612 (CVSS 9.9, escalation da utente interno) (S-106, S-107).
  • Traduzione dei formati: bug aperti su reasoning e tool call tra Responses, Messages e Chat Completions (P-08).
  • Integrazione con VS Code: la discovery dei modelli fallisce ("Invalid response format") (S-111); il cambio Plan→Agent con customendpoint ha un'issue aperta (S-076); i modelli BYOK custom endpoint possono non essere disponibili in WSL, SSH e Dev Container (riguarda tutto il BYOK) (S-077).

Hardening minimo (D-018, S-108)

  • Versione fissata (1.108.2); mai latest, main-latest, main-stable; digest e firma cosign in team.
  • Bind su 127.0.0.1 (il default è 0.0.0.0) (S-118). In rete: TLS e rete privata.
  • Agli sviluppatori solo virtual keys con scope e budget, mai la master key.
  • general_settings.disable_env_credential_login: true; SSO per l'Admin UI.
  • Ruota le chiavi se hai eseguito una versione compromessa.

4.2 Configurazione del gateway (config.yaml)

File completo: examples/litellm/config.yaml. Estratto senza le impostazioni di hardening (extra_body.provider, turn_off_message_logging, max_request_size_mb, allowed_file_extensions), descritte in 04 §9:

model_list:
  - model_name: claude-sonnet               # alias usato da VS Code
    litellm_params:
      model: anthropic/claude-sonnet-5-5    # prefisso provider / ID vendor
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: codex
    litellm_params:
      model: openai/responses/gpt-6.1-sol   # Responses API (D-015)
      api_key: os.environ/OPENAI_API_KEY
  - model_name: gemini                      # default stabile (D-016)
    litellm_params:
      model: gemini/gemini-4-argon          # gemini/ = AI Studio; senza prefisso = Vertex AI
      api_key: os.environ/GEMINI_API_KEY
  - model_name: gemini-pro                  # preview
    litellm_params:
      model: gemini/gemini-3.1-pro-preview
      api_key: os.environ/GEMINI_API_KEY
  - model_name: openrouter-gpt-oss
    litellm_params:
      model: openrouter/openai/gpt-oss-120b
      api_key: os.environ/OPENROUTER_API_KEY
  - model_name: hf-gpt-oss
    litellm_params:
      model: huggingface/groq/openai/gpt-oss-120b   # huggingface/<provider>/<org>/<model>

litellm_settings:
  drop_params: true

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  disable_env_credential_login: true

4.3 Configurazione di VS Code verso LiteLLM

  • Esegui la procedura comune (§3.0) con Custom Endpoint.
  • Inserisci in chatLanguageModels.json il contenuto di examples/vscode/chatLanguageModels.litellm.json.
  • Alla prima richiesta, inserisci nel prompt litellmKey la master key (profilo minimo) o una virtual key (profilo esteso).

Gruppo in formato OpenAI (apiType: chat-completions) per Codex, Gemini, OpenRouter, Hugging Face. Estratto: il file completo contiene anche openrouter-gpt-oss e hf-gpt-oss:

    { "id": "gemini",     "name": "LiteLLM · Gemini 4 Argon",           "url": "http://localhost:4000/v1/chat/completions", "toolCalling": true, "vision": true, "maxInputTokens": 112000, "maxOutputTokens": 16000 },
    { "id": "gemini-pro", "name": "LiteLLM · Gemini 3.1 Pro (preview)", "url": "http://localhost:4000/v1/chat/completions", "toolCalling": true, "vision": true, "maxInputTokens": 112000, "maxOutputTokens": 16000 }

Gruppo in formato Anthropic (apiType: messages) per Claude. Estratto: il file completo contiene anche claude-opus. Il formato Messages evita la perdita dei thinking_blocks con tool (D-019, S-110):

{
  "name": "LiteLLM (Anthropic format)",
  "vendor": "customendpoint",
  "apiKey": "${input:litellmKey}",
  "apiType": "messages",
  "models": [
    {
      "id": "claude-sonnet",
      "name": "LiteLLM · Claude Sonnet (messages)",
      "url": "http://localhost:4000/v1/messages",
      "toolCalling": true, "vision": true,
      "maxInputTokens": 112000, "maxOutputTokens": 16000,
      "requestHeaders": { "Authorization": "Bearer ${apiKey}" }
    }
  ]
}

Autenticazione con Messages. VS Code invia x-api-key (S-071). LiteLLM su /v1/messages documenta Authorization: Bearer e x-litellm-api-key (P-04); l'esempio LiteLLM usa x-api-key (S-028). L'header Authorization: Bearer ${apiKey} copre i due casi. ⚠️ Non attivare forward_llm_provider_auth_headers: con questa opzione LiteLLM inoltra x-api-key al provider (P-04).

Discovery. Non impostare url a livello di provider: la discovery dei modelli LiteLLM fallisce (S-111). Usa un url esplicito per ogni modello (D-019).

Token. I valori di maxInputTokens/maxOutputTokens sono prudenziali: adattali alla finestra di contesto reale. La somma non deve superare la finestra.

Gruppo in formato Responses (opzionale): usa "apiType": "responses" e "url": "http://localhost:4000/v1/responses". LiteLLM traduce Responses → Chat Completions per Anthropic e Gemini (S-029).

4.4 Profilo esteso: virtual keys per utente

Con PostgreSQL (01-Installazione.md §5.2) il gateway genera chiavi per utente con budget (S-020, S-031).

  • Genera una virtual key ⚠️ (parametri da verificare in S-031):
printf 'Authorization: Bearer %s\n' "$LITELLM_MASTER_KEY" \
  | curl -s http://localhost:4000/key/generate -H @- \
  -H "Content-Type: application/json" \
  -d '{"models": ["claude-sonnet", "gemini-pro"], "max_budget": 5, "metadata": {"user": "demo-wpc"}}'
  • Usa il valore key della risposta nel prompt litellmKey di VS Code.
  • Controlla la spesa nell'Admin UI: http://localhost:4000/ui.

Appendice A — GitHub Spec Kit con Copilot

Spec Kit implementa lo spec-driven development: la specifica guida l'agente nelle fasi constitution → specify → plan → tasks → implement (S-080).

A.1 Requisiti

  • Python 3.11+, uv, un agente supportato (GitHub Copilot), su Linux, macOS o Windows (S-080).

A.2 Installazione della CLI specify

  • Installa la CLI (S-081):
uv tool install specify-cli
  • (Raccomandato per il talk) Fissa una release. Ultima release: v1.3.2 (2026-11-06) (S-085):
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.3.2
# oppure da PyPI
uv tool install specify-cli==1.3.2
  • Verifica: specify version. Controlla gli aggiornamenti: specify self check (S-081).
  • Controlla i tool degli agenti installati: specify check (S-084).
  • Aggiorna, se necessario: uv tool install --force specify-cli (S-081).

A.3 Integrazione con GitHub Copilot

  • Crea un nuovo progetto con l'integrazione Copilot (S-080, S-081):
specify init my-project --integration copilot
cd my-project
code .
  • Oppure inizializza la cartella corrente (repository esistente):
specify init --here --force --integration copilot
Opzione Funzione
--integration copilot Genera i comandi per GitHub Copilot
--script sh | ps | py Tipo di script; default ps su Windows, sh sugli altri sistemi
--here Usa la cartella corrente
--force Conferma il merge in una cartella non vuota
--non-interactive Nessun selettore interattivo (CI); senza --integration il default è Copilot
--integration-options="--commands" Layout a comandi (agents + prompt files) al posto delle skill

L'opzione --ai non esiste più: è stata rimossa nella 0.10.0. Usa --integration (S-084, P-07).

  • Prima del primo commit, controlla i file generati (04 AZ-10). Gli script in .specify/scripts/ e le skill sono eseguiti dall'agente:
git status --short
git diff --stat

Gli script vanno in .specify/scripts/bash/, .specify/scripts/powershell/ o .specify/scripts/python/ (S-081). File generati per Copilot (S-083):

Layout File Invocazione
Skills (default) .github/skills/speckit-<comando>/SKILL.md /speckit-<comando>
Commands (--integration-options="--commands") .github/agents/speckit.<comando>.agent.md, .github/prompts/speckit.<comando>.prompt.md, merge di .vscode/settings.json agente speckit.<comando>

Le skill funzionano negli harness Copilot e Local (§2.3). Il layout a comandi usa prompt files: solo harness Local.
